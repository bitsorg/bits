# Unreleased

- **[Fix]** `bits cleanup --retain --mark-published-from` keys a CVMFS publish marker by the build's architecture and `<version>-<revision>`, which the bits-console publish record now names (`architecture`, `version_dir`): it used the console platform (`x86_64-el9` for `x86_64-el9-gcc14-opt`), so nothing was ever seen as published and the sweep released no certified content. A record entry that names a path is refused.
- **[Fix]** A network given in `--docker-extra-args` (`--network=…`, `--net …`) is the one the build container uses: bits appended `--network=host` after it, so both reached the engine.
- **[Fix]** A `%` in a `--reference-sources` path is taken as it is, and `--from-manifest` with a JSON file that is not an object says so: both ended in a traceback.
- **[Fix]** `bits sbom` (and the release SBOMs) render a manifest whose package `hash` is not a string, or whose licence nests more than 32 parentheses (not taken as an SPDX expression), instead of ending in a traceback.
- **[Change]** `bits cleanup --retain` removes a store or BUILD folder only when its name is a bits hash (40 hex digits), as the leftovers sweep does: it took 40 to 64.
- **[Fix]** `bits compliance --enforce` and the other orchestrator actions report an action the console answers without an id as it is, instead of a traceback (KeyError).
- **[Fix]** Two builds of one target started in the same second write their own build manifests (`bits-manifest-<target>-<time>-2.json`, ...) instead of the same file, and two bits processes in one work dir no longer race on the `latest` link's temporary name.
- **[Fix]** `bits sign --require-approval` takes the certifier only from `--certifier`, not from `$GITLAB_USER_LOGIN`: every pipeline has that variable and a pipeline variable overrides it, so whoever could set one named an admin, and the merge-request check behind it was never reached. The manifests CI passes `--certifier` (the merged merge request's author).
- **[Fix]** The merge request whose approvals `bits sign --require-approval` reads is the one that merged the commit (its merge, squash or head commit) into the pipeline's branch: the first merged one containing the commit counted, which could be an older one, or one into another branch.
- **[Improvement]** A build published without its NOTICE and source offer says so in its pipeline record (`compliance_files: false` in `BUILDS/by-pipeline/`), and `bits cvmfs release --pipeline` warns about it: writing them is best-effort, and the only trace was a warning in the publish log.
- **[Fix]** The release source offer (`LICENSE-SOURCE-OFFER.txt`) checks each source archive it names against an S3 store: one that is not there is marked "not archived" and warned about, instead of being offered as available for three years. A bits-store keeps sources apart, so there they are not checked.
- **[Fix]** `bits sign --require-approval` counts merge-request approvals only of a merged merge request, the one of the commit (`CI_COMMIT_SHA`): an open one (`CI_MERGE_REQUEST_IID`, or the first of `CI_OPEN_MERGE_REQUESTS` in a branch pipeline) counted too.
- **[Fix]** `bits sign` needs the BOMs to merge (`MANIFEST...`): without them it merged `<work dir>/MANIFESTS`, which holds no BOMs but the build manifests and the signed manifests fetched from the stores, and signed those again under its key.
- **[Change]** `bits build --cvmfs-prefix` is removed: it mounted the work dir at the CVMFS path in the container, the retired approach `--no-relocate` served; bits-console does not pass it. The `system:` `prefix`/`cvmfs_prefix` of the defaults (the CVMFS layout) and `BITS_CVMFS_PREFIX` are unchanged.
- **[Change]** `bits publish --no-relocate` is removed: it published the build host's installed tree unchecked, for the retired approach of building in the final `/cvmfs` path. Every package is published from its certified tarball, relocated to `--cvmfs-target`.
- **[Fix]** `bits cleanup` does not evict, and `bits cleanup --retain` does not sweep, a package a running build uses: each build lists the packages it touches in a file under `<work dir>/.in-use/`, held (flock) until the build exits. The build lock the module described was never taken, so only the sentinel's age protected a running build, and the retention sweep looked at no lock at all.
- **[Fix]** A CVMFS catalog fetched by hash (`bits q`, `bits cvmfs stage`) must be the object it was asked for: the digest of its stored bytes is compared with the hash (SHA-1, or the `-rmd160`/`-shake128` the hash names) and other bytes are refused, as is an object over 1 GiB compressed or decompressed; whatever answered was believed, so anyone on the plain-http path to the store could name any existing object as the subtree to graft.
- **[Feature]** bits-console backend: a build job records the host it ran on (`host` in `/ops/builds`), from the start of its log: the host the job names (`[setup] build host:`), else the runner's own name; finished builds recorded before get it once.
- **[Improvement]** A store tarball the signed-reuse gate checked is not hashed again for the build manifest: its digest is passed on.
- **[Improvement]** `bits sign --digest-cache FILE` hashes a store tarball once: each object's sha256 is kept in FILE with its key, ETag and size (which S3 sets), and an unchanged object is not downloaded again; it downloaded and hashed every tarball of every BOM on every run. Off by default: FILE's entries are signed as they are, so it must be writable by the signer only (never a CI cache other jobs restore).
- **[Improvement]** The build manifest is written at most every 5 seconds while packages are recorded (and before each build script, at the end and at exit; a killed build may miss the packages of its last seconds): it was written whole for every package, so a stack of 1000 reused packages serialised gigabytes of JSON.
- **[Fix]** `bits compliance PACKAGE…`, `bits deps` and `bits init` run the recipes' `prefer_system_check`/`system_requirement` snippets without credentials in the environment, as `bits build` does, and `bits preload` traces a package on the host the same way: they ran with the whole shell environment (S3 keys, store and GitLab tokens).
- **[Fix]** `bits compliance --enforce` deletes a store folder only when it holds tarballs of the BOM entry's package and version (`<package>-<version>[-<revision>].<arch>.tar.gz`), none of them of another package (a recipe, or one the store's BOMs or rev-index name) whose name begins with `<package>-`: it matched by name prefix, so an entry for `foo` naming the hash of `foo-bar` deleted that build.
- **[Fix]** `bits cleanup --retain` does not sweep an architecture whose signed manifest verifies but certifies nothing: a transiently empty certification made it remove every install not in the last builds.
- **[Fix]** Signing through bits-console (`python -m bits_helpers.sign_console`) keeps waiting for the approval when the console answers a 5xx or cannot be reached for a moment; one 502 ended a wait that would have succeeded.
- **[Fix]** A bits-console call with `--insecure` (or `--console-insecure`) no longer switches TLS verification off for the later calls of the same process; a `Console` keeps its own setting.
- **[Fix]** `bits cvmfs stage`: when re-reading the repository head after a moved base, opening the prepare lock or recreating the scratch directory fails, it says so; such errors were reported as a missing `cvmfs_swissknife`.
- **[Fix]** Only the subcommand is moved ahead of the options: an option value equal to `build`, `init`, `clean`, `doctor` or `deps` was moved too, so `bits build --disable clean ROOT` built a package called `clean`.
- **[Fix]** A package's cleanup sentinel stands beside its install tree, `.packages/<arch>/[<family>/]<package>/<version>` with the effective architecture: for a package of a family, an `architecture: share` or an own-hash one it was under the build architecture without the family, so `bits cleanup` recorded 0 bytes, "evicted" only the sentinel and left the install, and `--retain` deleted the sentinel. An old sentinel of such a package frees nothing when evicted and is dropped by the next `--retain`; `share` and own-hash packages need `--all-architectures`.
- **[Fix]** `bits cleanup --retain --dry-run` removes nothing: it unlinked the sentinels of install trees that are gone and dangling `BUILD/*-latest` links.
- **[Improvement]** A secret given on the command line (`--s3-secret-key`, `--prepub-token`, `--certifier-token`, `--gitlab-token`, and `--token` of `bits cvmfs publish`/`release`) is warned about, naming the environment variable to use instead: others on the host see it in the process list, and CI logs echo it.
- **[Fix]** `--console-insecure` no longer lets a token go over plain http: `bits login` (the store token comes back), and `bits compliance --enforce` and `bits store rm --stale-boms` (their requests carry the GitLab token), need https or a local console, and the option only skips the certificate check there. `bits sign --sign-via-service` sent the CI ID token to any URL containing `://localhost` (`http://localhost.example.org`). The unauthenticated pre-approval of `bits publish` may still use http on a testbed.
- **[Fix]** A `&group` in an admin policy, and the bits-console admin and developer groups, count only the active members at Developer level or above: every member counted, a Guest or a blocked account too.
- **[Fix]** `bits sign`, and bits-orchestrator's certification, refuse a BOM entry that names a group other than its directory's (`manifests/<group>/` under the manifests given) or the run's `--group`: the entry's own group won, so under `manifests/lhcb/` one saying `common` was signed as `common` without an lhcb approval (`--changed-groups`, which now needs every manifest in a group directory). A BOM can no longer name its directory either, and in the orchestrator such an entry vouches for no group in a withdrawal.
- **[Fix]** `bits compliance --enforce --key` signs each signed manifest that lists a restricted package again without it, once it verifies against the trusted keys, keeping only the entries its signer could certify (one bits-orchestrator numbered is left to it). A key that cannot be used is refused before anything is removed. It re-certified the platform from every BOM in the store, unapproved ones included, as group `common`.
- **[Fix]** `bits cvmfs publish` refuses a `.bits-view.json` entry that is absolute or climbs out (`..`), and the view fails: a climbing entry placed a link outside the staging directory, on the publish host.
- **[Fix]** `bits publish PACKAGE` publishes the tarball the signed manifests or the build manifest certify, as `bits cvmfs publish` does: another packing of the hash is replaced by the certified object from the store, and a tarball no manifest records is refused. It took the work dir's tarball, or the store's, unchecked.
- **[Fix]** `bits cvmfs publish` refuses a package whose tarball sha256 neither the signed manifests nor the build manifest record; it published it unchecked. A build now records the sha256 of an already installed package too, from its tarball in the work dir, hashed once (it gets a .sha256 sidecar): on a warm build host most packages had none.
- **[Fix]** `bits cvmfs publish` and `bits publish PACKAGE` refuse a tarball packed by a bits older than 2026-07-11: its own `relocate-me.sh`, which publishing runs, has no `BITS_RELOCATE_STRIP_PP` and would double `<arch>/<pkg>/<ver>` in the published paths. One packed before 2026-10-09 is refused where the target contains its build's `PKG_DIR` (a `--cvmfs-prefix` build), which that script rewrites twice. Rebuild such a package.
- **[Fix]** `bits publish --release-view NAME -n` only says where it would place the view; it built the view for real.
- **[Fix]** `bits cvmfs publish` does not rewrite a dependency path in a `.bits-relocate` entry that leaves the package through a directory link, as `relocate-me.sh` now refuses one.
- **[Fix]** `bits publish PACKAGE --cvmfs-target … -n` only says what it would publish, from where and to where; it unpacked, relocated and submitted the package to prepub for real.
- **[Fix]** `--build-nice` with rootless podman gives a container no `--cpu-shares` when no cgroup controller is delegated to the user at all (no systemd user session); the check missed that case, and the container could not start.
- **[Fix]** A package published to CVMFS (`bits publish PACKAGE`, `bits cvmfs publish`) carries its `.build-hash`, as an installation does, so `--symlink-packages-from` with the strict policy (the default) can reuse it; the tarball does not contain it (it is written at install).
- **[Fix]** `relocate-me.sh` also refuses a `.bits-relocate` entry that leaves the package through a symbolic link in it, which `sed -i` would otherwise edit.
- **[Improvement]** A build that takes again a revision claim of its own hash in an S3 store (one a failed build left) writes it again, so `bits store rm --stale-rev-markers`, which goes by a claim's age, never removes the claim of a build still running.
- **[Improvement]** A build reads a version's revision markers from an S3 store (`b3://`) up to eight at a time, not one after another.
- **[Improvement]** A reused tarball that was packed on this host or passed the signed-reuse check is unpacked without being decompressed once more to list its members first (the tar-slip guard stays for every other one).
- **[Improvement]** A source archive extracted before and unchanged since (its size and modification time, recorded in `.bits_extracted`) is not read again to work out its strip depth: a resumed or repeated build of a large source no longer decompresses it first.
- **[Fix]** `relocate-me.sh` reads a package's `.bits-pkginfo` (`OP`, `PP`, `PH`, `PKG_DIR`) instead of running it, so that file cannot run commands (a tarball without it keeps its own script, and a package's `post-relocate.sh` still runs); a value with `$` or a backquote (but `PP=${PKGPATH:-…}`) stops the relocation. A `.bits-relocate` entry that is absolute or climbs out with `..` is refused.
- **[Fix]** A node remembers a signed manifest's sequence per issuer, architecture and signing key: another trusted key naming the same issuer with a high number can no longer make the node refuse that issuer's real manifests. What a node remembered before is carried over.
- **[Fix]** `bits cvmfs publish --wait` waits for all its jobs within one `--wait-timeout` (prepub runs them together); past it, each job left is asked once more, not waited for. Each job had the whole timeout in turn, so a run could wait hours.
- **[Fix]** `bits cvmfs publish` and `bits publish PACKAGE` publish the package's own directory of a tarball that packs more than one `.meta.json`: the one at `<package>/<version>`, else the only shallowest one; several at that depth stop the publish. It took the first one the directory walk met.
- **[Feature]** `bits store ls|rm --stale-rev-markers [--older-than DAYS]`: the revision claims (`MANIFESTS/rev-index/`) that no stored tarball carries, older than DAYS (default 7), left by builds that failed; narrowed by `--arch`, `--package` and `--version`. S3 stores.
- **[Fix]** `bits cvmfs publish` checks a package's tarball against the store's signed manifests when they list it (`--trust-manifest`, default the store's; `none` to skip), not only against the build manifest's `tarball_sha256`: the build manifest is a file in the work dir, and one without the field was published unchecked.
- **[Fix]** The container sandbox takes the network out of the `docker run` argument list, not out of the command text, so a quoted `-e` value or `--docker-extra-args` word that contains `--network=…` is left as it is.
- **[Fix]** What a package's own scripts get where credentials are (native builds, `$(...)` sources, stage hooks, relocate scripts, system checks) no longer points at the ssh or gpg agent, an askpass helper, `NETRC`, `KUBECONFIG`, `DOCKER_CONFIG`, `AWS_CONFIG_FILE`, a Kerberos ticket or a grid proxy. A ticket, proxy or kubeconfig at its default path stays readable there: only a sandbox keeps it from a build.
- **[Fix]** The macOS build sandbox also denies reading `~/.git-credentials`, `~/.pypirc`, `~/.npmrc`, `~/.config/gh`, `~/.kube`, `~/.config/gcloud` and cargo's credentials, and the S3 keys, store token and GitLab token files wherever bits is configured to keep them (`BITS_AWS_KEYS_FILE`, `BITS_STORE_TOKEN_FILE`, `BITS_GITLAB_TOKEN_FILE`, the site's `paths.*`).
- **[Fix]** A downloaded source that cannot be copied into the package's source directory (disk full, permissions) stops the download with that error; it was only logged, and the build failed later at the extraction.
- **[Fix]** A recipe's `prefer_system` and system-requirement checks, and `pip download` of a source package (which runs its build code), get no credentials (pip keeps its own `PIP_*` settings and proxies). They had all but the S3 keys, or everything.
- **[Feature]** `--container-engine podman` (or `BITS_CONTAINER_ENGINE=podman`) runs bits' containers with podman instead of docker, rootless: no root daemon, and a recipe leaving its container has only the user's privileges. For `bits build`, `deps`, `doctor` and `status`; scripts bits starts see the choice in `$BITS_CONTAINER_ENGINE`.
- **[Change]** With `--docker`, the recipe sandbox (`--sandbox auto` or `podman`) is the build container itself: it runs with `--network=none` unless the recipe allows the network (`sandbox_network: off`), and sees only its mounts. The nested podman inside it is gone: rootless podman cannot start in a container running as the user ("failed to reexec: Permission denied"), so it needed podman in the image and privileges that defeat the protection. A recipe that fetches during its build (pip or cargo through bits-store, git-lfs) needs `sandbox_network: off` under `--sandbox auto`.
- **[Fix]** The podman sandbox without `--docker` (`--sandbox-image`) mounts bits, the recipes, the git mirror and `/cvmfs` read-only at their paths, and a development package's source. Only the work dir was mounted, so the build could not reach the recipes' patches, bits' own scripts, the mirror, reused packages or a development source.
- **[Change]** `bits certify` only asks for the passkey approval; the store's bits-orchestrator certifies the build. The certification merge request in a manifests repository is retired: a store without bits-orchestrator is refused before anything is uploaded (there its key holder signs with `bits sign`), and `--manifests-remote`, `--ref`, `--gitlab-token` and `--certifier` are accepted with a warning and ignored.
- **[Fix]** `bits publish PACKAGE --cvmfs-target` publishes the package's tarball, relocated to the target in a working copy (the work dir's tarball, else fetched from `--remote-store`). It copied the installed tree, which is already relocated to the work dir, so CVMFS got paths into the work dir; and it ran the installed tree's `relocate-me.sh`, which rewrote the local installation instead of the copy. With `--no-relocate` the installed tree is still what is published.
- **[Fix]** `bits cvmfs-publish` publishes the tarball the manifest certifies: the work dir's when its sha256 is the manifest's `tarball_sha256`, else that object fetched from the stores (`--store`, comma-separated and tried in order; default `$BITS_REMOTE_STORE`, else `$REMOTE_STORE`), else nothing. It published whatever sat in the work dir, which can be the build's own packing of a hash the store already held, or a file changed since. A manifest without the field (older bits) is published as before, with a warning.
- **[Improvement]** REFERENCE and FAQ say that a recipe lifting the sandbox's network block (`sandbox_network: off`) is a deliberate exception for now: no command-line or defaults setting can keep it on, so reviewing a recipe includes that line.
- **[Fix]** The macOS build sandbox no longer lets a build read the user's credentials: `~/.bits` (store and GitLab tokens), `~/.ssh`, `~/.aws`, `~/.netrc`, `~/.gnupg`, `~/.docker/config.json` and the keychains, under `$HOME` and the account's own home, are denied after the disk-wide read allow (a work dir inside one stays readable). A recipe that clones over ssh or reads `~/.netrc` itself now fails in the sandbox.
- **[Fix]** `bits publish PACKAGE --cvmfs-target` makes its working copy and its tar under the work dir (`TMP/`, or `--scratch-dir`), not the system temp dir, and removes the copy whatever stops the publish: a multi-GB package could fill a small `/tmp` twice over, and a failed copy or relocation left it there. A work dir it may not write needs `--scratch-dir`.
- **[Fix]** `bits cvmfs-publish` unpacks a tarball only when no member is absolute or climbs out (`..`), and without restoring its owners, as the build's own unpack does: publish took it unchecked.
- **[Fix]** `bits cvmfs-publish` repeats a submission that met a 5xx, or a network error before its upload began (any, for a staged one), up to five times with a fresh signature, when it names the path it publishes (`identity_path`, which prepub re-checks): one 502 failed the package and the run. An upload prepub cuts off is still not repeated.
- **[Improvement]** `bits cvmfs-publish` reads and hashes each package's tree for its fingerprint only on a dry run, which prints it: every real publish read and hashed everything it published once more for nothing.
- **[Fix]** An HTTP(S)/FTP source download gives up after 120 s without an answer, keeps nothing when the body is shorter than its Content-Length, and leaves no temporary file on an error: a stalled server held the worker (and every build waiting on its sentinel), and a truncated archive was cached as complete.
- **[Fix]** A source URL with a login (`https://user:password@host/…`) is fetched with it: encoding it raised a TypeError, reported only at debug level as a failed download.
- **[Fix]** A cached source that fails its declared checksum (`--enforce-checksums`, or `checksum_mode: enforce`) is removed, so the next run fetches it anew: the bad copy stayed in the cache and every later build stopped on it.
- **[Fix]** Polling a prepub job stops at once on a 4xx (other than 429) with its status and body: a wrong secret, a clock skew against the signature, or an unknown job was polled again for up to 30 minutes (an hour with `--wait`).
- **[Fix]** A `pip://` source runs `pip download` with an argument list, no shell, and `pip=` may name only `pip`, `pip3`, `pip3.N` or an absolute path to one of them: the URL's options went into a shell command run on the host. `pip_options` are no longer expanded by a shell (`$VAR`, `~`). No recipe in the workspace sets `pip=` or `pip_options`.
- **[Fix]** A `git` source is fetched with argument lists, no shell: its branch, tag and repository went unquoted into one shell command run on the host, and a part starting with `-` is now refused (it would be read as an option).
- **[Fix]** A source is copied into its build's source dir, and download dirs made, without a shell: the source URL's last segment went unquoted into `mkdir -p …; cp …`, run on the host, so a `;` or `$(…)` in it ran as a command.
- **[Improvement]** When an HTTP store does not answer (not a 404), bits warns once per run that what the store holds is built or fetched from upstream instead. Before, only each request's `GET … failed` error showed it: the build went on as if the store simply had none.
- **[Fix]** A `b3://` read store keeps this work dir's version links, as the HTTP backend does: it removed them all and a hash-only store gives none back, so the revision scan found no local revision and a second local variant of a version took `local1` again, replacing the first one's install.
- **[Fix]** An HTTP store download writes its own temporary file (per process and thread): two fetches of one file, by two bits runs in one work dir, wrote into the same `<file>.tmp`.
- **[Fix]** A read store and a write store of different kinds always get one helper each: an `rsync` or `s3://` read store with a `b3://` write store handed the b3 URL to the rsync or s3cmd backend as its write store.
- **[Fix]** A restricted build whose revision marker bits-store refuses is kept on this host with a warning, as when the build itself is refused: the marker error stopped it.
- **[Fix]** After uploading a tarball to a `b3://` store, bits reads back the sha256 the store holds and records that one (and that the object is not this build's): two builds of one hash that both found no object both uploaded, and the one overwritten recorded a sha256 the store no longer had. This narrows the race; an upload finishing after the read-back is still missed.
- **[Fix]** Stamping a legacy `b3://` object's sha256 keeps its other metadata (`bits-by`, who uploaded it) and content type: the metadata self-copy replaced all of it with the sha256 alone.
- **[Fix]** With a write store, a new counter revision is reserved in the store (its rev-index marker) when it is picked, before the build; one another hash took meanwhile is skipped for the next free number. Two builds of one version running at once both took the same number, and one replaced the other's install path. bits-store markers are write-once; an S3 store's are where it supports `If-None-Match`, else the last writer wins. A build that fails keeps its number for a retry of the same hash (others skip it). A store that cannot be asked keeps the number, as before.
- **[Change]** A native build (no `--docker`) runs its script without the run's credentials (tokens, keys, URLs holding a login, proxies and package indexes included), as a container build already does: a recipe gets one only with `-e NAME`. It inherited all but the S3 keys. (ALICE's xjalienfs tests need `-e JALIEN_TOKEN_CERT -e JALIEN_TOKEN_KEY`.)
- **[Change]** `bits build -e NAME` without a value hands the build script NAME's value from bits' environment, as `docker run -e NAME` does, without it appearing on a command line; it set NAME empty.
- **[Improvement]** bits warns about a signed manifest without `expires`, once per manifest and run: where no sequence is remembered, an older signed copy put back would be accepted. `bits certify` writes none unless given `--valid-days` (the orchestrator writes 30 days). REFERENCE says to keep `$BITS_TRUST_SEQUENCE_STATE` on runners with a fresh home.
- **[Improvement]** A reused package's installed `.meta.json` keeps who built it: the tarball's own record is added as `origin` (this run's record stays, as before). Left out when the tarball has none bits can read.
- **[Fix]** The HTTP and `b3://` stores download the object named as the package's tarball (`<pkg>-<version>-<rev>.<arch>.tar.gz`), as bits-store does: they took the first object listed under the hash, whatever its name.
- **[Fix]** A `--symlink-packages-from` stage whose marker was cut short (bits killed while writing it) is staged again: the build stopped with "Cannot symlink package" on every run.
- **[Fix]** The build script no longer looks up gcc before the recipe (`cversion`, `cpath`, used nowhere): where no gcc was on PATH it stopped in its preparation without a message.
- **[Fix]** A reused tarball is unpacked into an emptied `TMP/<hash>`: files an interrupted unpack of the same hash left there were installed with the package.
- **[Fix]** A tarball-source package whose recipe drops its last patch is extracted again: the source tree kept the dropped patches, and the new build (its hash changed) was made from them.
- **[Fix]** A `SYMLINK_STAGE` hook runs without the run's credentials (tokens, keys, URLs holding one): it ran on the host with the whole environment.
- **[Fix]** A recipe's `$(...)` source entry is evaluated without the run's credentials (tokens, keys, URLs holding one), as publish runs a package's scripts: it ran on the host with the whole environment.
- **[Fix]** A `hook:` given as a YAML list (`POST_INSTALL: [rpm, sbom]`) runs its hooks as `rpm,sbom` would, and an empty one runs none: bits ran a hook named `rpm_sbom` (with `--docker` it stopped with a TypeError), did not find a `SYMLINK_STAGE` list, and stopped on an empty hook without `--docker`.
- **[Fix]** A recipe's `hook_params` reach its hooks as written, no longer expanded: a value with `"` broke the build script, and `$` or a backquote in one was expanded. A name that is not a shell variable name is refused.
- **[Fix]** A build's environment reaches the shell quoted whole, name and value: a recipe's `hook:` name is part of a name, and one with `;` ran a command on the host before the container started (`--docker`).
- **[Improvement]** A failed build's report reads only the last 16 MiB of its log for the excerpt; it read the whole log into memory, which can be gigabytes, once per failure with `--builders`.
- **[Improvement]** The failure report of a build (host, `xcodebuild -version` on macOS, log excerpt) is gathered only when the build fails; it was made for every package, and twice for development packages.
- **[Fix]** A package or version with `+`, `(` or another character a regular expression reads otherwise (`tauola++`, `1.0+cms`) no longer breaks the revision scan: its version links were not parsed, so a revision already taken could be handed out again; with `(`, or `++` on Python 3.8–3.10, the pattern did not compile and bits stopped.
- **[Fix]** At startup bits keeps the tarball download sentinels of another bits run on the same host (same PID namespace); it removed every one, so both runs downloaded the same file. It removes a sentinel whose owner is gone, that holds our own PID or that is older than the 600 s a waiter waits for it, now also those under `SOURCES/cache/`, which it missed.

## Scheduled builds and CI on push

At CERN nothing changes; **elsewhere, an empty `/etc/bits/site.d/10-CERN.yaml` turns CERN's values off** and a file of your own sets yours. `bits doctor` shows the files in effect (USERGUIDE "Where defaults come from").
- **[Improvement]** `bits certify` and `bits compliance --enforce` take the console URL from the site configuration's `console.backend_url` too, so at CERN they need no `--console`.

## The bits-console service (for operators)

The service behind bits-console (`console-backend`, part of bits and deployed from the
commit bits-console pins) gains a worker, `python -m console_backend.orch.worker`, that
records and queues builds, certifies them and runs scheduled builds. It keeps its state in
a SQLite database, upgraded automatically when the worker starts; after an upgrade the API serves `/ops` only once the worker has started.

### Records and audit
- **[Feature]** Every change the service makes (retry or cancel a pipeline, pause a build host, …) is an action with a JSON schema: it may need an approval (an automated advisor can only propose one), the requester's rights are checked again when it runs, it is retried with backoff, and one runs at a time per subject (`/ops/actions`). Everything is written to a hash-chained event log (`/ops/events`), copied to the audit-log service of bits-services and checked against that copy on every pass (`GET /ops/outside`; `python -m console_backend.orch.outside verify|status|clear`, and `recover` to rebuild a restored database from the copy).
- **[Feature]** Builds: every build pipeline is recorded from GitLab, its outcome taken from its jobs, with the builds it published from the store's build index (`GET /ops/builds`, `/ops/builds/{pipeline}`); CI jobs report publishes and failures (`POST /ops/ci/published|failed`, with an ID token for the service). Each job's time is split into queued, setup, build and, per package, publish (`phases`), with the build host it ran on and, for a failed job, where it stopped (`build`, `certify`, `publish` or `finish`, from the marks bits-console's build job writes), so a failed publish is told from a failed build. The worker also writes the console's CVMFS status file, `cvmfs-status.json` (`BITS_ORCH_CVMFS_STATUS`).
- **[Feature]** Failures: failed jobs are read from their logs (or from `bits-build.log` when GitLab cut the log), with secrets removed, and repeats of the same error are grouped into issues; known causes are named (`GET /ops/issues`, `/ops/issues/{id}`, `/ops/failures`, `/ops/signatures`; `BITS_ORCH_BACKFILL_DAYS` also reads older failures).
- **[Feature]** `bits trace PATH`: who built, published and approved a file on CVMFS, from its package's `.meta.json` and the service (`GET /ops/trace`; cvmfs-prepub's records with `BITS_ORCH_PREPUB_URLS`).
- **[Feature]** `GET /ops/worker`: the worker's last pass and which of its steps fail, since when (admins; the error text for overall admins).
- **[Change]** Any signed-in user reads, for the community named (`?community=`), its builds (without who approved their certification, a build's variables or its events), its failed jobs and its queued builds (without who queued them or the build hosts): the phone app's read-only view. Vulnerabilities, approvals and actions stay with the admins.

### Approvals and certification
- **[Feature]** Approvals live in the service's database with their passkey signature: they survive a restart, each use is counted, and they expire or can be revoked (`GET /approvals`, `POST /approvals/{id}/revoke`). Besides a build's pre-approval, one passkey approves a queued batch of builds, and a schedule has a standing approval, bound to what it builds and the groups it certifies for, for 1 to 100 builds or up to 30 days. A copy of the database is made daily (`BITS_ORCH_BACKUP_DIR`).
- **[Feature]** Certification by the service. It first computes each certification beside the CI's and compares them (`GET /ops/certifications`, `/ops/certifications/summary`), then certifies pre-approved builds itself (`BITS_ORCH_CERTIFY=1`, first under `CANARY/` to compare with the CI's).
- **[Feature]** The service keeps the set of certified builds and each version of it, from bits-manifests (`GET /ops/certified`, `/ops/certified/bom/{sha256}`).
- **[Feature]** With `BITS_ORCH_OWNS_SET=1` the service owns the set of certified builds: it writes the signed manifests (`MANIFESTS/`, numbered per architecture with `sequence`), mirrors each version of the set to bits-manifests and writes `MANIFESTS/orchestrator.json`, so that bits commands know the service owns the set; the backend's signing routes are gone. Admins ask for a group's certification of a build, or of all builds containing a package, to be withdrawn (`decertify`, `decertify-package`), and the worker takes it out of the signed manifests. A half-written manifest is repaired, and with an audit copy the service signs only while the copy is up to date.
- **[Feature]** Builds are certified as soon as they are in the store (their pipeline running or succeeded), not after their CVMFS publish; `/ops/certify` also serves community admins and says whether the service owns the set.
- **[Feature]** The service can run without holding a GitLab token or a store key: it reaches both through the credentials proxy of bits-services (`credentials-proxy`, `BITS_CRED_PROXY_AGENT_SOCKET`), into which bits-services' `make unlock` loads the keys from an encrypted bundle. `BITS_ORCH_STORE_ANONYMOUS=1` reads a public store without credentials.

### Build queue and build hosts
- **[Feature]** The build queue (`BITS_ORCH_QUEUE=1`, `POST /ops/queue`): the console's builds wait in the service, not in GitLab, and start one per free build host. A host whose runner is offline is not free, a build GitLab drops before it starts is queued again, and `GET /ops/queue` shows GitLab's refusals as a pause.
- **[Change]** The build hosts are the build project's GitLab runners tagged `bits-host-<name>` (their architecture from `bits-build-<arch>`), no longer `config/build-hosts.yaml` (`BITS_ORCH_BUILD_HOSTS` is gone): a runner registered, removed or retagged changes them within 5 minutes. A host whose runners are all paused shows as `paused`, not offline; a build whose host or architecture is not among them waits an hour before it is refused, and a runner the token may not see is left out and logged.
- **[Feature]** An overall admin pauses and resumes a build host's runners and refreshes its builder images (`host.pause`, `host.resume`, `host.refresh`), and prunes its work directory to the free space saved for it (`host.prune`, 200 GiB unless set with `PUT /ops/hosts/{host}/prune-target`). `GET /ops/admin/ci-var?key=BITS_DESIRED_REF` gives any admin the bits version the runners are set to.

### Help chat
- **[Feature]** A help chat on a local model (Ollama on the service's host, `BITS_CHAT_URL`): signed-in users ask how to use bits, or why a build failed, and the answer comes from the markdown files of the bits repositories (bits, the services, CVMFS publishing, every community's) and of bits-console, read from GitHub and GitLab into a full-text index, and from what the service recorded of the build (with the end of its logs, read when asked, and what changed since the last successful build of the package), citing its sources. The model gets no tools; votes on answers are kept 90 days for evaluation (`console-backend/chat-eval/`); with an embedding model (`BITS_CHAT_EMBED_MODEL`) questions find the docs by meaning as well as by their words.

### Scheduled builds
- **[Feature]** Nightly schedules (`GET/POST /ops/schedules`, `PUT/DELETE /ops/schedules/{id}`, `/pause`, `/resume`), in the instance's time zone (site setting `console.time_zone`). The worker queues a night's builds at its time: one per platform and variant, a night missed by less than 6 hours still built, a cell whose last build still runs skipped, a night that cannot be built as configured not run, certified under the schedule's standing approval.
- **[Feature]** A schedule's variants: defaults chains put before its own, so one schedule builds its platforms × variants each night; Run again takes cells.
- **[Feature]** What became of each night: each build is followed to `running`, `passed`, `failed` (and where), `skipped` or `not_run` (no free build host for 12 hours); `GET /ops/nightlies` is the nightly matrix, `POST /ops/schedules/{id}/run` Run now or Run again.
- **[Feature]** CI on push: a schedule may follow branches (`watch`); the worker reads their heads every `BITS_ORCH_WATCH_S` seconds and, once the pushes have settled for 5 minutes (30 at most) and none of the schedule's push builds is still running, builds every cell, neither certified nor published. They show as rows of their own in the nightly matrix.
- **[Fix]** A nightly build uses its schedule's defaults with the community's `defaults_overlay` (without it a Testbed nightly would publish to production's repository), also sent as `DEFAULTS` so that its CVMFS target follows the same defaults, and carries its night's weekday as `--day`, so a nightly layout's `{day}` is the night's even when the build starts after midnight UTC. A schedule's extra arguments may not give `--defaults`.

### Vulnerabilities and licences
- **[Feature]** SBOM scans (`BITS_ORCH_SCANNER_URL`, the sbom-scanner of bits-services, with grype): every published build is scanned, again when the vulnerability database is newer and when a newer pipeline publishes the build. The scans index which builds contain a package, for the package search. `GET /ops/builds/{pipeline}/sbom` serves a build's SBOM to any signed-in user, with its findings for the admins of its community.
- **[Fix]** A build made with the command line (`bits publish`, certified from its pre-approval) is recorded once certified, under pipeline 0 with the approved group as its community, and is scanned and searched like a pipeline's; in upgrade plans and licence analyses it has a release line of its own, without a platform.
- **[Feature]** Risk over time: once a day the worker records each release's open findings and their risk, by severity (a release is a community's top-level package), and its earlier builds at their publish days (`GET /ops/sbom/history?community=&days=`, the Vulnerabilities page's chart).
- **[Feature]** Triage of findings (`not_affected`, `false_positive`, `will_not_fix`, with a reason and an expiry, revocable), for one version, every version, every package, or every vulnerability of a package; triaged findings, and those of host tools and of what only they or the build need, are not counted.
- **[Feature]** Upgrade plans from the scans, per release line and across communities, in waves (known exploited, within the major version, major), minding version pins; licence and dependency analysis: licence conflicts along runtime paths, unknown licences, copyleft reach, the most depended-on, build-only and unneeded packages, and what changed since a line's previous build.

## Signed reuse, trust and certification
- **[Fix]** Trust manifests are fetched afresh by every build (a cached copy was never refreshed), revalidated with their ETag, and verified and parsed from the same bytes; a failed fetch trusts nothing from that manifest instead of an older copy.
