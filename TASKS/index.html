    Find what you need¶

    What people most often want to do with bits, and where the docs explain it. The FAQ has short answers to more specific questions.

    Getting started¶

    Install bits and check my machine¶

    Install bits, then let bits doctor check the machine and say what is missing. See: Installing bits, Building natively: what to install, bits doctor.

    Choose the platform to build for (--architecture)¶

    Pass a platform name such as x86_64-el9; the compiler and build type come from --defaults. Pick one with pre-built binaries to reuse them. See: Before you start: pick the platform to build for, Platforms, Finding a platform with pre-built binaries.

    Build my community's software¶

    Check out your community's recipe repository and build inside it. Each community's README has the exact commands. See: Check out your community's recipe repos, Check, then build, ALICE, the LCG stack, ATLAS, LHCb, Key4hep, SHiP.

    Use what I built (load its environment)¶

    bits enter opens a shell with the packages loaded; bits load changes the current shell (with eval, or the shell helper); bits setenv runs one command. See: Use the built environment, Enter a sub-shell with modules loaded, Load / unload in the current shell.

    Stop repeating the same options¶

    bits use records options such as the platform, defaults and store, so later commands take them. See: Configuration, Config mode — record persistent settings with bits use, Where defaults come from.

    Building¶

    See what will be built or downloaded, before building¶

    See: Previewing a build: --dry-run, bits status, Preview what will rebuild.

    Understand why a package is rebuilt (or reused)¶

    A package is reused when its hash matches: the hash covers its recipe, sources, dependencies and settings. See: How bits works, Hashing and reproducibility.

    Build faster, or several packages at once¶

    See: Building several packages at once, Speed up large builds, Build memory-hungry packages without exhausting RAM.

    Build for another Linux, or for ARM (--docker)¶

    See: Building in a container, Build for a different OS or architecture (Docker), Cross-compilation via QEMU.

    Debug a failed build¶

    The failed build's directory and its full log are kept. See: Debug a failed build, Error handling in recipes — how failures are detected.

    Work on a package's source, or on a local copy of recipes¶

    See: Develop and iterate on a single package, Build with the local checkout, Check out a recipe repository and develop against it.

    Free disk space¶

    See: Cleaning up, Evict old packages to free disk space.

    Recipes and defaults¶

    Write a recipe¶

    A recipe is <package>.sh, in lower case: a YAML header, a line with ---, then the build script. See: Writing Recipes, Minimal recipe, Recipe Format Reference, Writing Recipes with bits-recipe-tools.

    Build another version without editing the recipe¶

    See: Override a package version without editing the recipe, Defaults Profiles.

    Choose compiler and build type (--defaults)¶

    Defaults profiles (defaults-<name>.sh) are chained with ::, on top of release. See: Defaults Profiles, Composing profiles (LCG).

    Choose which experiment's recipes bits uses¶

    Recipe repositories come through repository providers, listed in bits-providers. See: How bits uses this repository, Repository Provider Feature, Defining a repository provider.

    Make source downloads reproducible (checksums)¶

    See: Enforce reproducible source downloads with checksums, Checksum verification, bits checksums.

    The console and CI¶

    Build and publish from bits-console¶

    See: Connect to bits-console, Browse and trigger a build, Getting access.

    Define a schedule: build every night, or on each push¶

    A slot on the console's Schedules tab builds a package at its nightly time, on each commit to the branches it follows, or both. See: Schedule nightly builds, Build on each push (CI), Defining a slot.

    Publish the latest version automatically, in its final destination¶

    A slot can also publish where a Production build goes, not in a per-day nightly directory: on each commit, at its own time, or by Publish now (e.g. bits itself). See: Publish the latest version to its final destination, Publishing the latest version.

    Find out why a build failed in the console¶

    The console's Failures page and Explain on a failed build say what went wrong. See: Debug a failed build, Builds, certification and SBOMs.

    Add or configure a community in the console¶

    See: Adding a new community, Configuring a community.
